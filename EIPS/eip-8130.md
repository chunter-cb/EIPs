## Abstract

This proposal introduces a new [EIP-2718](./eip-2718.md) transaction type and an onchain Account Configuration system that together provide account abstraction: custom authentication, call batching, and gas sponsorship. Accounts register actors with onchain authenticator contracts. Transactions declare which authenticator to use, enabling nodes to filter transactions without executing arbitrary wallet code. No EVM changes are required. The contract infrastructure is designed to be shared across chains as a common base layer for account management.

## Motivation

Account abstraction proposals that delegate validation to wallet code force nodes to simulate arbitrary EVM before accepting a transaction. This requires full state access, tracing infrastructure, and reputation systems to bound the cost of invalid submissions.

This proposal separates authentication from account logic. Each transaction explicitly declares its authenticator, a contract that takes a hash and signature data and returns the authenticated actor. This makes validation predictable: wallets know the rules, and nodes can see exactly what computation a transaction requires before executing it. Instead of simulating arbitrary code, nodes filter on authenticator identity. New signature algorithms are introduced through authenticator contracts and standardized through the canonical authenticator set.

## Specification

### Overview

An account authorizes one or more **actors** which are credentials permitted to act on its behalf. Each actor is bound to an **authenticator**, an onchain contract that checks a signature and returns the actor's identity (`actorId`). An account's actors, their authenticators, and their permissions are held in the **Account Configuration Contract** at `ACCOUNT_CONFIG_ADDRESS`.

A new [EIP-2718](./eip-2718.md) transaction type (`AA_TX_TYPE`) names the authenticator that authenticates it. Because the authenticator is declared explicitly, a node can tell exactly what computation a transaction requires and reject unknown authenticators before executing any code. Validation reads the account's configuration, runs the named authenticator, and checks the resolved actor's permissions; execution then dispatches the transaction's calls. The specification covers the authentication/authorization model ([Authenticators](#authenticators)), onchain management ([Account Configuration](#account-configuration)), the wire format and gas ([AA Transaction Type](#aa-transaction-type)), and creation/actor changes ([Account Changes](#account-changes)).

Accounts are portable across EVM chains; see [Portability](#portability). The Account Configuration Contract's deployed bytecode is the canonical, normative artifact; contract-internal details (storage layout, slot derivation, packing) are defined by that bytecode and are not restated here (see [Contract Pinning](#contract-pinning)).

#### Account Types

This proposal supports three paths for accounts to use AA transactions, all accounts work the same once initialized (EOA is initialized by default).

| Account Type | How It Works | Key Recovery |
|--------------|--------------|--------------|
| **EOAs** | EOAs send AA transactions using their existing secp256k1 key via native ecrecover. If the account has no code, the protocol auto-delegates to `DEFAULT_ACCOUNT_ADDRESS` (see [Block Execution](#block-execution)). Accounts MAY override with a delegation entry in `account_changes` or a standard [EIP-7702](./eip-7702.md) transaction | Wallet-defined; EOA recoverable via standard transactions |
| **Existing Smart Contracts** | Already-deployed accounts (e.g., ERC-4337 wallets) register actors via `importAccount()` on the Account Configuration Contract | Wallet-defined |
| **New Accounts (No EOA)** | Created via a create entry in `account_changes` with CREATE2 address derivation; runtime bytecode placed at address, actors + authenticators configured, `calls` handles initialization | Wallet-defined |

### Authenticators

Each actor is associated with an authenticator, a contract that performs signature authentication. The authenticator *authenticates* the actor (it returns the actor's `actorId`); scope and policy then *authorize* what that authenticated actor may do. The authenticator address is stored in the actor's config (see [Account Configuration](#account-configuration)). All authenticators implement `IAuthenticator.authenticate(hash, data)`. After authentication, the protocol validates the returned `actorId` against the actor's config and checks its scope against the authorization context.

Authenticators are executed via STATICCALL. Authenticator addresses MUST NOT be delegated accounts; reject if the code at the authenticator address starts with the delegation indicator (`0xef0100`).

`K1_AUTHENTICATOR` (`address(1)`) is a protocol-reserved address for native secp256k1 authentication. When the protocol encounters this address as an authenticator, it performs ecrecover directly rather than making a STATICCALL. The `data` portion is interpreted as raw ECDSA `(r || s || v)`, and the returned `actorId` is `bytes32(bytes20(recovered_address))`. The same identity serves both the implicit default EOA and any explicitly registered k1 actor; the actor config alone distinguishes a full-owner EOA from a scoped key, so actors can be explicitly registered with `K1_AUTHENTICATOR` to use native ecrecover with a custom scope, without requiring a deployed authenticator contract. `address(0)` is considered empty.

Any contract implementing `IAuthenticator` can be permissionlessly deployed and registered as an actor's authenticator. Registration is always permitted in EVM execution, enabling use cases such as wallet-defined recovery methods. Whether a given authenticator is admitted for block-level AA authentication depends on the chain's acceptance model (see [Authenticator Acceptance](#authenticator-acceptance)).

#### Canonical Authenticator Set

This specification defines a canonical authenticator set to be accepted in the 8130 transaction type. The initial canonical set is below.

| Name | Algorithm | Authenticator | `actorId` Derivation |
|------|-----------|---------------|----------------------|
| k1 | secp256k1 | `K1_AUTHENTICATOR` (native sentinel) | `bytes32(bytes20(recovered_address))` |
| p256 | P-256 | `P256_AUTHENTICATOR` | `keccak256(abi.encodePacked(x, y))` |
| passkey | WebAuthn / FIDO2 | `PASSKEY_AUTHENTICATOR` | `keccak256(abi.encodePacked(x, y))` |
| delegate | Signature delegation | `DELEGATE_AUTHENTICATOR` | `bytes32(bytes20(delegated_address))`: signatures from `delegated_address` are valid for the registering account (see [Delegate Authenticator](#delegate-authenticator)) |

The canonical contracts are deployed at deterministic CREATE2 addresses and specified in the contract section (see [Contract Pinning](#contract-pinning)). The set is expected to remain small but grow as new algorithms are adopted (e.g. post-quantum).

#### Authenticator Acceptance

Which authenticators a node admits for block-level AA authentication is fixed by one of two models, chosen per chain:

- **Consensus (default).** The [canonical authenticator set](#canonical-authenticator-set) is fixed by consensus and enumerated per fork. The work a transaction requires is known from the authenticator address before execution. A transaction is accepted iff its authenticator is in the canonical set for the active fork. The canonical set is native optimized and charged less gas on a schedule.
- **Mempool policy.** A chain MAY instead make acceptance a mempool policy, not a consensus constraint. Block validity places no restriction on the authenticator: any `IAuthenticator` is accepted and executed via metered STATICCALL (the [Metered Calls](#intrinsic-gas) profile). Nodes apply their own mempool filters to bound invalid-submission cost. Chains may natively optimize any authenticator on the 8130 transaction type during a fork as above.

Both models resolve the actor identically once the authenticator returns an `actorId`; non-admitted authenticators remain fully usable within ordinary EVM execution.

#### Delegate Authenticator

The delegate authenticator lets one account act on behalf of another. An account **A** authorizes an actor with `authenticator = DELEGATE_AUTHENTICATOR` and `actorId = bytes32(bytes20(B))`; thereafter any key that can authenticate as **B** may authenticate as **A**, bounded by the `scope` **A** grants that delegate actor (normal [Actor Scope](#actor-scope) rules).

**Wire format.** The auth blob's `data` (following the 20-byte authenticator address, per [Signature Format](#signature-format)) is:

```
data = delegated_account (20 bytes)   // B
    || nested_auth                     // authenticator (20 bytes) || data, a normal auth blob for B
```

**Constraints**:

- **No nesting (depth-1):** the nested authenticator MUST NOT be the delegate authenticator; delegation cannot chain.
- **Nested authenticator MUST be canonical (8130 path):** on the 8130 transaction path the nested authenticator MUST belong to the [canonical authenticator set](#canonical-authenticator-set), keeping total work bounded and enshrinable.

The requirement that **B**'s nested actor be admin (signing authority is the `scope == 0x00` predicate) is enforced by the pinned delegate authenticator contract (see [Contract Pinning](#contract-pinning)).

### Account Configuration

Each account can authorize a set of actors through the Account Configuration Contract at `ACCOUNT_CONFIG_ADDRESS`. This contract handles actor authorization, account creation, change sequencing, and delegates signature authentication to onchain [Authenticators](#authenticators). Its deployed bytecode is the canonical artifact; the protocol reads its storage directly during validation (see [Contract Pinning](#contract-pinning)).

Actors are identified by their `actorId`, a 32-byte identifier the authenticator derives from public key material. Each actor's config carries an authenticator address, a `scope` byte, and an optional `expiry` (`uint48` Unix seconds; `0` = no expiry; invalid once `block.timestamp > expiry`); when `scope` includes `POLICY` (`0x02`) it additionally carries a signed policy commitment and a manager address (see [Actor Policies](#actor-policies)). Actors are revoked by clearing their config; the self-actor (`actorId == bytes32(bytes20(account))`) is the one exception (see [Self-Actor](#self-actor)). The config reserves bytes that MUST be zero on write; nonzero reserved bytes act as an implicit version gate (new-format configs fail to apply through legacy deployments rather than dropping restrictions). Actor enumeration is off-chain via `ActorAuthorized`/`ActorRevoked` logs.

#### Self-Actor

The **self-actor** (`actorId == bytes32(bytes20(account))`) is the account's own identity, authenticated by native secp256k1 `ecrecover`, never an external authenticator contract.

**Implicit EOA authorization** is the one protocol-visible rule: a native secp256k1 signature recovering to the account authenticates as the self-actor with admin scope and no expiry (`scope == 0x00`, `expiry == 0`) whenever `DEFAULT_EOA_REVOKED` is not set, letting every existing EOA send AA transactions immediately without prior registration. Validation resolves this per [Validation](#validation) (scoping restriction: [Implicit EOA Rule Scoping](#security-considerations)).

The self-actor may be scoped, disabled, or replaced by a non-secp256k1 self authenticator through config changes, and `createAccount`/`importAccount` set `DEFAULT_EOA_REVOKED` by default (a quantum-safe default that leaves no native owner live unless one is named in `initial_actors`). How these states are represented and applied is internal to the pinned Account Configuration contract (see [Contract Pinning](#contract-pinning)): the protocol either fast-paths the native-secp256k1 self on a raw read or calls the contract directly to apply owner changes.

#### Actor Scope

The scope byte is a permission bitmask of **grants**. `0x00` means unrestricted (all contexts) and is also the account's **admin** predicate: any check requiring an "admin" actor is exactly `scope == 0x00`. Any non-zero value grants only the contexts whose bits are set. Reads are fail-closed: a context is authorized only when `scope == 0x00` or the corresponding grant bit is present. Unknown bits grant nothing. All future scope bits MUST be pure grants. An actor whose scope sets only unknown bits is stored verbatim but authorizes no context.

| Bit | Value | Name | Context |
|-----|-------|------|---------|
| 0 | `0x01` | SENDER | Ungated initiation: `sender_auth`; may originate transactions to any `call.to`. Carries operational authority (unless combined with `POLICY`) — also satisfies `verifySignature()` (ERC-1271 signing) |
| 1 | `0x02` | POLICY | Gated initiation: `sender_auth`; may originate transactions only to the actor's `policy_manager` (see [Actor Policies](#actor-policies)) |
| 2 | `0x04` | NONCE | Permits a restricted actor to use sequenced `nonce_key`s for sender-context transactions (see [Actor Nonce Scope](#actor-nonce-scope)) |
| 3 | `0x08` | SELF_PAYER | Self-pay gas: authorizes paying the account's own gas when `payer == sender` |
| 4 | `0x10` | SPONSOR_PAYER | Sponsor gas: authorizes acting as `payer_auth` for a different sender (`payer != sender`) |
| 5–7 | | (spare) | Reserved for future pure grants |

**Operational authority.** An actor is *operational* when it can originate calls to any target: `operational := admin (scope == 0x00) || (SENDER && !POLICY)`. ERC-1271 signing (`verifySignature()`) is **not** a grant; it is authorized for any operational actor. A `POLICY` actor is never operational and MUST NOT sign raw hashes (a signature would act off its policy gate); scoped signing is expressed at the account layer via an approved-hash pattern driven by a `POLICY` key (see [Actor Policies](#actor-policies)).

**Admin and composition.** Config-change authority (`authorizeActor`, `revokeActor`, `applySignedActorChanges`, delegation) is exactly `scope == 0x00`; every account is born with a scope-0 root (the implicit EOA, or an unrestricted actor named at create/import) and restricted keys are grants below it (see [Why Admin Is Scope Zero](#why-admin-is-scope-zero)). Grants compose: whenever `POLICY` is set the call is gated to the `manager` regardless of `SENDER` (wallets SHOULD NOT set `SENDER | POLICY`); `POLICY | SELF_PAYER`, `POLICY | NONCE`, and `POLICY | SPONSOR_PAYER` compose likewise, and with `SPONSOR_PAYER` sponsor authority is **not** gated. `authorizeActor` stores any combination verbatim; combination semantics are checked at the point of use, and `getActorConfig`/`authenticateActor` MUST return stored scope bytes unmodified.

Scope authorization is applied only after an authenticator returns an `actorId`. For `sender_auth`, require `scope == 0x00 || (scope & (SENDER | POLICY)) != 0`. For self-pay (payer account == sender) require `SELF_PAYER`; for sponsorship (payer account ≠ sender) require `SPONSOR_PAYER` on the `payer_auth`-resolved actor; for `verifySignature()` require operational; for config-change `auth` require admin. See [Validation](#validation) for the full flow.

#### Actor Nonce Scope

`NONCE` (`0x04`) grants a restricted actor access to ordered (sequenced) `nonce_key`s for **sender-context** transactions.

| Actor | `nonce_key` allowed |
|-------|----------------------|
| Admin (`scope == 0x00`) | Any `nonce_key`, including `NONCE_KEY_MAX` (nonceless), freely |
| Restricted, `NONCE` unset | `nonce_key == NONCE_KEY_MAX` only (nonceless) |
| Restricted, `NONCE` set | Any `nonce_key`, including `NONCE_KEY_MAX` — the full 2D key space |

This makes nonceless (`NONCE_KEY_MAX`) the default for every restricted (non-admin) actor. `NONCE` constraints apply to **sender-context** transactions only; `payer_auth` consumes no payer-side sequence and is unaffected. The check is enforced by the protocol; see [Validation](#validation).

#### Actor Expiry

The protocol enforces one rule: an actor is **live** at `now` (the inclusion block timestamp) iff `expiry == 0 || now <= expiry`, evaluated at inclusion. It checks only the acting key's own `expiry` and never walks authorizer lineage, so a live admin's authorization survives that admin's own later expiry or revocation; removal requires an explicit `revokeActor`.

Note for wallets: `expiry` is set only by a config change (initial actors are always non-expiring), and SHOULD be placed only on non-admin actors. Using it on an admin (`scope == 0x00`) can break valid change chains for cross-chain actor-change replay and account sync, so an admin SHOULD NOT expire unless the wallet owner deliberately plans for it and keeps a non-expiring owner in place.

#### Actor Policies

Actor policies gate a key to a single `manager` contract that enforces application-defined authority on the account's behalf, for example a session key limited to a spend cap or a small set of targets.

`POLICY` selects whether an actor is gated; gating is determined by the scope bit alone. When set, `policyData` MUST be exactly `manager` (20 bytes) ‖ `commitment` (32 bytes), written verbatim to `policy_manager`/`policy_commitment`; neither field need be nonzero. A zero `commitment` is a valid "no parameters" value. When unset, `policyData` MUST be empty and prior policy slots are cleared.

| `POLICY` | Gate: `call.to` MUST equal | `policyData` at authorize |
|----------------|----------------------------|---------------------------|
| unset | (no gate) | empty |
| set | the actor's `manager` (`address(0)` = no productive target) | `manager` (20) ‖ `commitment` (32) |

A policy-bearing actor may call exactly one target: its configured `manager`. The contract at that target reads the actor's `commitment` (via [`getPolicy`](#reference-implementation)), validates presented parameters against it, and carries out the approved action. The protocol's only responsibility is the single-target gate.

A key that should be enforced by the account's own code sets `manager = account`. Because protocol dispatch originates the call from the account itself (`msg.sender == account`), this is only meaningful with policy-aware wallet code; code that implicitly trusts self-calls (e.g. a standard `executeBatch`) turns such a key into an unrestricted one (see [Security Considerations](#security-considerations)).

**Scope.** `POLICY` is the gated initiation grant. It MAY combine with `SELF_PAYER` (session key self-pays gas, bounded by balance and `expiry`) and with `NONCE` (sequenced `nonce_key`). A `POLICY` key is not operational and cannot sign ERC-1271; scoped signing SHOULD use an account-level approved-hash pattern (Safe `approveHash` precedent) driven by the `POLICY` key.

**Enforcement.** The gate is applied during [Call Execution](#call-execution). Validity does not read `policy_commitment` or `policy_manager`. Policy state is keyed by `(account, actorId)`; clearing on revocation and target-held parameters are covered under [Policy State on Revocation](#security-considerations).

#### 2D Nonce Storage

Nonce state is managed by a precompile at `NONCE_MANAGER_ADDRESS`. The protocol reads and increments nonce slots directly during AA transaction processing; the precompile exposes a read-only `getNonce()` interface to the EVM.

The transaction carries two nonce fields: `nonce_key` (`uint256`) selects the nonce channel, and `nonce_sequence` (`uint64`) is the expected sequence number within that channel.

| `nonce_key` Range | Name | Description |
|-------------------|------|-------------|
| `0` | Standard | Sequential ordering, mempool default |
| `1` through `NONCE_KEY_MAX - 1` | User-defined | Parallel transaction channels defined by wallets |
| `NONCE_KEY_MAX` | Nonce-free | No nonce state read or incremented |

##### Nonce-Free Mode (`NONCE_KEY_MAX`)

When `nonce_key == NONCE_KEY_MAX`, the protocol does not read or increment the nonce counter and `nonce_sequence` MUST be `0`. Replay protection relies on `expiry` (which MUST be non-zero) plus `replay_id` deduplication state that is a fixed-capacity **circular buffer** and is **consensus state**, not per-node bookkeeping: a `seen` map (`replay_id → expiry`) holds live entries, and a ring of `replay_id`s in insertion order evicts the oldest once expired. Per transaction the protocol rejects if `seen[replay_id]` is still live, evicts the ring slot at the pointer if it holds an expired entry (rejecting if the buffer is full of still-live entries), then writes the new `replay_id`, sets `seen[replay_id] = expiry`, and advances the pointer. Because both the liveness check and the full-buffer rejection decide block validity, the capacity MUST be a protocol constant or explicit chain parameter (`REPLAY_BUFFER_CAPACITY`), identical for every node — a per-node capacity would split consensus. It MUST be at least `peak accepted nonce-free throughput × NONCE_FREE_EXPIRY_WINDOW`, so an entry always expires before its slot is reused; entries are ephemeral, so there is no permanent state growth. The maximum accepted `expiry` window (`NONCE_FREE_EXPIRY_WINDOW`) is likewise an explicit chain parameter, sized together with `REPLAY_BUFFER_CAPACITY`.

###### Replay Identifier

Nonce-free (`NONCE_KEY_MAX`) transactions have no nonce slot to key deduplication and replacement on, so each carries a **replay identifier** that names the *logical* transaction independent of its fees and authorization blobs. Standard and 2D transactions (`nonce_key != NONCE_KEY_MAX`) do **not** use `replay_id`; they are deduplicated and replaced by `(sender, nonce_key, nonce_sequence)` under the standard nonce rules (see [Mempool Replacement](#mempool-replacement)).

```
REPLAY_ID_TYPE = 0x7901

replay_id = keccak256(REPLAY_ID_TYPE || rlp([
  chain_id, resolved_sender, expiry,
  account_changes, calls, metadata,
  payer
]))
```

`resolved_sender` is recovered via ecrecover (EOA path) or taken from the `sender` field (configured-actor path), keeping the identifier unique per sender. `replay_id` excludes the fee fields (`max_fee_per_gas`, `max_priority_fee_per_gas`, `gas_limit`) so a fee bump does not change identity, and excludes `sender_auth`/`payer_auth` (non-deterministic and re-signable). It includes `payer` (the address, not `payer_auth`): retargeting at a different payer is a different logical transaction and MUST produce a different `replay_id`. The full transaction hash MUST NOT be used for nonce-free deduplication or replacement (rationale in [Security Considerations](#security-considerations)).

###### Mempool Replacement

Fee-bump replacement candidates are keyed by `(sender, nonce_key, nonce_sequence)` for standard and 2D transactions and by `(sender, replay_id)` for nonce-free transactions (block builders MUST NOT include two nonce-free transactions with the same `(sender, replay_id)` in one block). In both modes a replacement MUST increase `max_priority_fee_per_gas` by at least the node's minimum bump (e.g. ≥10%) and MUST be independently fully valid, including a fresh `payer_auth` when sponsored (`payer_auth` commits to the fee fields, so the payer must re-sign). For nonce-free transactions, changing `payer` yields a new `replay_id` rather than a replacement.

#### Account Lock

Account lock freezes actor configuration. The lock state, the change sequences, an account-flags byte, and the default-EOA (self-actor) config share the account-state slot; the exact packing is internal to the contract (see [Contract Pinning](#contract-pinning)). The protocol-visible fields are:

| Field | Description |
|-------|-------------|
| `multichain_sequence` | Change-sequence counter for `chain_id 0` (`uint64`) |
| `local_sequence` | Change-sequence counter for the local chain (`uint64`); `> 0` doubles as the initialized flag |
| `flags` | `DEFAULT_EOA_REVOKED` disables the secp256k1 self-actor; `LOCKED` freezes actor configuration; `UNLOCK_INITIATED` selects how `lock_union` is interpreted |
| `lock_union` | While `UNLOCK_INITIATED` is clear, holds `unlock_delay` (seconds, `uint16` range): the notice required before config can change, which nodes read for rate-limit tiering. While set, holds `unlocks_at` (the timestamp at which unlock takes effect) |

When `LOCKED`, all actor-config changes and delegation are rejected on both paths; the only permitted operation is `unlock`. The `unlock_delay` is bounded to the `uint16` range (~18.2h max), preventing an account from self-bricking config rotations.

##### Lock Operations

Lock state changes only through `applySignedLockChanges`, a dedicated admin-authorized entry point accessible in the EVM only.

```
LOCK_CHANGE_TYPEHASH = keccak256(
  "SignedLockChange(address account,uint256 chainId,uint8 op,"
  "uint16 unlockDelay,uint64 sequence)")
// op: 1 = lock, 2 = unlock

applySignedLockChanges(address account, uint8 op,
                       uint16 unlockDelay, bytes calldata auth)
```

Lock uses the local account channel. The digest binds `chainId = block.chainid` and `sequence = local_sequence` (the **current** counter value); the contract rejects a mismatch and, on success, increments `local_sequence` — the same sign-current-then-increment convention as transaction nonces and local config changes (which share this counter). `auth` is a standard `authenticator \|\| data` blob (see [Signature Format](#signature-format)) validated as **admin** (`scope == 0x00`) against `account`. Anyone may relay; authorization comes from the signature.

**Lifecycle** — `lock`, then `unlock`, with no other actions in between:

1. **Lock** (`op = 1`): only from the unlocked state. Sets `LOCKED` and stores `unlock_delay = unlockDelay`. Rejected if already locked; the delay cannot be changed while locked.
2. **Unlock** (`op = 2`): only from `LOCKED` with no pending unlock; `unlockDelay` MUST be `0`. Sets `UNLOCK_INITIATED` and `unlocks_at = block.timestamp + unlock_delay` (from the stored delay).
3. **Effective unlock**: once `block.timestamp >= unlocks_at`, the account is unlocked and config changes resume; flags and `lock_union` are lazily cleared by the next op. Locking again requires a fresh `lock`.

#### Account Import

`importAccount(address account, uint256 chainId, InitialActor[] calldata initialActors, bytes calldata signature)` is a one-time call that registers an already-deployed account into the Account Configuration Contract with an initial actor set. `chainId` is the replay domain of the import signature: `0` = multichain (valid on every chain); otherwise it MUST equal `block.chainid`. The call is rejected when:

- `chainId` is neither `0` nor the current chain.
- The account already has 8130 state: **either** change-sequence channel is non-zero. Import is a one-time bootstrap requiring both channels empty. A locked account is always caught here, since `lock` is a signed local config change that has advanced `local_sequence`.

The `signature` is validated against the account via [ERC-1271](./eip-1271.md) `isValidSignature(digest, signature)`, binding the initial actor set to the account's existing authorization logic. `digest` is a typed `ActorInitialization` struct hash:

```
ACTORCONFIG_TYPEHASH =
  keccak256("ActorConfig(address authenticator,uint8 scope,uint48 expiry)")

ACTOR_TYPEHASH =
  keccak256("Actor(bytes32 actorId,ActorConfig config,bytes policyData)"
            "ActorConfig(address authenticator,uint8 scope,uint48 expiry)")

ACTOR_INITIALIZATION_TYPEHASH =
  keccak256("ActorInitialization(bytes32 salt,uint256 chainId,Actor[] initialActors)"
            "Actor(bytes32 actorId,ActorConfig config,bytes policyData)"
            "ActorConfig(address authenticator,uint8 scope,uint48 expiry)")

// Per-actor. Imported actors carry scope and policyData like create; expiry is always 0.
configHash_i = keccak256(abi.encode(ACTORCONFIG_TYPEHASH, authenticator_i, scope_i, 0))
actorHash_i  = keccak256(abi.encode(ACTOR_TYPEHASH, actorId_i, configHash_i, keccak256(policyData_i)))

digest = keccak256(abi.encode(
    ACTOR_INITIALIZATION_TYPEHASH,
    bytes32(bytes20(account)),                               // salt, bound to the account address
    chainId,
    keccak256(abi.encodePacked(actorHash_0, ..., actorHash_n))
))
```

This typed (EIP-712-style) struct hash intentionally omits the EIP-712 domain separator (preventing phishing via standard wallet signing flows). Imported actors are always non-expiring: implementations MUST hash `expiry = 0` into every `configHash_i` and MUST NOT accept an actor-provided expiry. `policyData` follows `authorizeActor`'s frozen rule and is hashed into `actorHash_i`; unlike create, `manager = account` is expressible here. On success, `importAccount` sets `DEFAULT_EOA_REVOKED` (parity with `createAccount`); an owner who wants to keep the native key includes the self-actorId as a `K1_AUTHENTICATOR` entry in `initialActors`.

#### Delegation Indicator

The delegation indicator is the [EIP-7702](./eip-7702.md) mechanism for pointing an account's code at a shared implementation. An EOA sending its first AA transaction is auto-delegated to `DEFAULT_ACCOUNT_ADDRESS` when it has no code (see [Block Execution](#block-execution)), and accounts MAY set or clear delegation via a [Delegation Entry](#delegation-entry). The indicator MUST be supported on 8130 chains even when standalone [EIP-7702](./eip-7702.md) transactions are not enabled.

An account is delegated when its code is exactly `0xef0100 || target`, where `target` is a 20-byte address. Delegated accounts MAY originate transactions, and all code-executing operations targeting a delegated account MUST load code from `target` instead of the indicator.

`DEFAULT_ACCOUNT_ADDRESS` SHOULD implement [ERC-1271](./eip-1271.md) by delegating to the Account Configuration Contract's `verifySignature()`, and SHOULD implement token receiver hooks (ERC-721, ERC-1155) to safely receive assets.

### AA Transaction Type

A new [EIP-2718](./eip-2718.md) transaction with type `AA_TX_TYPE`:

```
AA_TX_TYPE || rlp([
  chain_id,
  sender,             // Sender address (20 bytes) | empty for EOA signature
  nonce_key,          // uint256: nonce channel selector
  nonce_sequence,     // uint64: sequence number
  expiry,             // Unix timestamp (seconds)
  max_priority_fee_per_gas,
  max_fee_per_gas,
  gas_limit,
  account_changes,    // Account creation, config change, and/or delegation operations | empty
  calls,              // [[call, ...], ...] where call = rlp([to, data]) | empty
  metadata,           // opaque attribution/annotation bytes | empty
  payer,              // empty = sender-paid, payer_address = specific payer
  sender_auth,        // raw ECDSA r||s||v (EOA, sender empty) | authenticator || data (configured actor)
  payer_auth          // empty = self-pay | authenticator || data = sponsored (same format as sender_auth)
])

call = rlp([to, data])   // to: address, data: bytes
```

#### Field Definitions

| Field | Description |
|-------|-------------|
| `chain_id` | Chain ID per [EIP-155](./eip-155.md) |
| `sender` | Sending account address. **Required** (non-empty) for configured actor signatures. **Empty** for EOA signatures; address recovered via ecrecover. The presence or absence of `sender` is the sole distinguisher between EOA and configured actor signatures. |
| `nonce_key` | `uint256` nonce channel selector. `0` for standard sequential ordering, `1` through `NONCE_KEY_MAX - 1` for parallel channels, `NONCE_KEY_MAX` for nonce-free mode. |
| `nonce_sequence` | `uint64` expected sequence number within `nonce_key`. Must match current sequence for `(sender, nonce_key)`. Incremented after inclusion regardless of execution outcome. Must be `0` when `nonce_key == NONCE_KEY_MAX`. |
| `expiry` | `uint64` Unix timestamp (seconds); encoded as a canonical minimal-length RLP integer. Transaction invalid when `block.timestamp > expiry`. A value of `0` means no expiry. Must be non-zero when `nonce_key == NONCE_KEY_MAX`. |
| `max_priority_fee_per_gas` | Priority fee per gas unit ([EIP-1559](./eip-1559.md)) |
| `max_fee_per_gas` | Maximum fee per gas unit ([EIP-1559](./eip-1559.md)) |
| `gas_limit` | Maximum gas budget for sender-intrinsic gas and call execution (see [Intrinsic Gas](#intrinsic-gas)). Payer authentication is metered separately and does not draw from `gas_limit` |
| `account_changes` | **Empty**: none. **Non-empty**: array of typed entries: create (`0x00`), config change (`0x01`), delegation (`0x02`). See [Account Changes](#account-changes) |
| `calls` | **Empty**: none. **Non-empty**: array of call phases; see [Call Execution](#call-execution) |
| `metadata` | **Empty**: none. **Non-empty**: opaque attribution/annotation bytes. See [Transaction Metadata](#transaction-metadata) |
| `payer` | Gas payer identity. **Empty**: sender pays. **20-byte address**: this specific payer required. See [Payer Modes](#payer-modes) |
| `sender_auth` | See [Signature Format](#signature-format) |
| `payer_auth` | Payer authorization. **Empty**: self-pay. **Non-empty**: `authenticator \|\| data`, same format as `sender_auth`. See [Payer Modes](#payer-modes) |

#### Intrinsic Gas

**Intrinsic gas** follows the standard Ethereum meaning: the total cost to include the transaction, here including both the sender's authentication (`sender_auth_cost`) and the payer's (`payer_auth_cost`).

The **formula structure** below (its components and what each accounts for) is normative. The absolute values in the [normative constants table](#normative-constants) are the recommended **Explicit Accounting** schedule reflecting current EVM access and data-availability costs ([EIP-2929](./eip-2929.md) / [EIP-2028](./eip-2028.md)); a chain MAY reprice them or MAY instead adopt the **Metered Calls** profile (see [Accounting Profiles](#accounting-profiles)). `REPLAY_BUFFER_CAPACITY` and `NONCE_FREE_EXPIRY_WINDOW` are consensus parameters, not repriceable schedule values.

```
intrinsic_gas = AA_BASE_COST + tx_payload_cost + nonce_key_cost + bytecode_cost
              + account_changes_cost + auto_delegation_cost + sender_auth_cost + payer_auth_cost
```

**Sender-intrinsic gas** is intrinsic gas excluding payer authentication and is bounded by `gas_limit`; the gas available to `calls` follows from it:

```
sender_intrinsic_gas    = intrinsic_gas - payer_auth_cost
execution_gas_available = gas_limit - sender_intrinsic_gas
```

`payer_auth_cost` is metered **outside** `gas_limit` and charged to the payer on top of it, under **both** accounting profiles. It does not draw from `gas_limit` and cannot reduce the gas available to `calls`; this makes the gas available to `calls` a function of sender-signed fields alone (rationale in [Why payer_auth Is Metered Outside gas_limit](#rationale)). `sender_auth_cost`, by contrast, is included in `gas_limit`, which both sender and payer sign over.

**Charging shares.** `account_changes_cost` splits into a **validation share** (per config-change entry: the entry's auth cost plus one sequence-check read; charged on every inclusion, including when phase 0 reverts; chained entries each charged in full; per skipped already-applied entry, one read) and an **application share** (per initial/authorized actor slot write, per `policy_manager`/`policy_commitment` write when `POLICY` is set, per delegation entry, and `bytecode_cost` for a create entry). The application share plus `bytecode_cost` is statically derivable from the parsed entries, so it is a known amount charged immediately before call phase 0; application cannot run out of gas mid-write. Future change types MUST keep the application share statically derivable.

**Charging on a phase-0 revert.** When call phase 0 reverts, the transaction is still charged: base and payload costs, `nonce_key_cost`, `sender_auth_cost`, the `account_changes` validation share, `auto_delegation_cost` if performed, the gas phase 0 consumed to the revert, and `payer_auth_cost` (outside `gas_limit`). Under Explicit Accounting, the `account_changes` application share (including `bytecode_cost`) is refunded: it prices state growth, and the rollback means no growth occurred. Under Metered Calls no refund rule applies — the reverted application and phase 0 are charged per ordinary EVM metering of the reverted scope, which already prices exactly the work performed. All other unused gas is refunded to the payer in both profiles. A transaction cannot revert its way out of paying for authorization it consumed.

##### Normative Constants

The formula structure above (its components and what each accounts for) is normative. This is the single table of normative constants; the gas values are the Explicit Accounting schedule.

| Component | Accounts for | Explicit Accounting value |
|-----------|--------------|---------------------------|
| `AA_BASE_COST` | Fixed AA-path overhead (decoding, sender/actor resolution, nonce-mode dispatch, receipt assembly), excluding components broken out separately | 15,000 gas |
| `tx_payload_cost` | Per-byte data availability over the entire RLP-serialized transaction | 16 gas/non-zero byte, 4 gas/zero byte (per [EIP-2028](./eip-2028.md)) |
| `nonce_key_cost` | Nonce-mode state access | nonce-free (`NONCE_KEY_MAX`): 13,000; first use of a `nonce_key`: 22,100; existing `nonce_key`: 5,000 |
| `bytecode_cost` | Create-entry deployment (`0` if no create entry) | 32,000 (deployment base) + 200 gas per deployed byte |
| `account_changes_cost` — validation share | Per config-change entry, charged on every inclusion (see [charging shares](#intrinsic-gas)) | auth cost (same model as `sender_auth_cost`) + 2,100 (sequence-check SLOAD); 2,100 per skipped entry |
| `account_changes_cost` — application share | Per-slot writes, charged only when phase 0 commits | 22,100 per initial/authorized actor slot (+22,100 each for `policy_manager`/`policy_commitment` when `POLICY` set); 4,600 per delegation entry; `bytecode_cost` for a create entry |
| `auto_delegation_cost` | Delegation-indicator deposit when a code-less `sender` is auto-delegated (`0` otherwise) | 4,600 gas (200 × 23 bytes for `0xef0100 \|\| address`) |
| `sender_auth_cost` / `payer_auth_cost` | Authenticator execution + actor-config read (`payer_auth_cost = 0` for self-pay) | authenticator execution + 2,100 (one cold `actor_config` SLOAD) |
| `REPLAY_BUFFER_CAPACITY` | Nonce-free replay ring-buffer capacity (consensus) | chain parameter (see [Nonce-Free Mode](#nonce-free-mode-nonce_key_max)) |
| `NONCE_FREE_EXPIRY_WINDOW` | Max nonce-free `expiry` window (consensus) | chain parameter (see [Nonce-Free Mode](#nonce-free-mode-nonce_key_max)) |

##### Accounting Profiles

A chain selects one profile to realize the formula. **Both yield identical state roots and identical transaction validity**; they differ only in how the cost is computed, and both meter `payer_auth_cost` outside `gas_limit`.

- **Explicit Accounting** (L2 / Base profile, recommended). The protocol reads Account Configuration and nonce state via raw-slot reads and charges the fixed schedule in the [constants table](#normative-constants).
- **Metered Calls** (L1 profile). Validation performs `CALL`/`STATICCALL` into the pinned contracts and gas is ordinary EVM metering of the known bytecode; no schedule is applied beyond `AA_BASE_COST` and `tx_payload_cost`. Because the bytecode is pinned by codehash (see [Contract Pinning](#contract-pinning)), the metered cost is deterministic across nodes.

The profiles yield identical validity and state roots but MAY differ in gas charged, including on a phase-0 revert (Explicit Accounting refunds the pre-priced application share; Metered Calls charges the reverted scope as metered).

#### Signature Format

Signature format is determined by the `sender` field:

**EOA signature** (`sender` empty): raw 65-byte ECDSA signature `(r || s || v)`. The sender address is recovered via ecrecover.

**Configured actor signature** (`sender` set):

```
authenticator (20 bytes) || data
```

The first 20 bytes identify the authenticator address. When the authenticator is `K1_AUTHENTICATOR`, `data` is raw ECDSA `(r || s || v)` and the protocol handles ecrecover natively. For all other authenticators, `data` is authenticator-specific.

#### Signature Payload

Sender and payer use different type bytes for domain separation, preventing signature reuse attacks:

**Sender signature hash** and **payer signature hash**, all tx fields through `payer`, excluding `sender_auth` and `payer_auth`:

```
keccak256(AA_TX_TYPE || rlp([
  chain_id, sender, nonce_key, nonce_sequence, expiry,
  max_priority_fee_per_gas, max_fee_per_gas, gas_limit,
  account_changes, calls, metadata, payer
]))

keccak256(AA_PAYER_TYPE || rlp([
  chain_id, sender, nonce_key, nonce_sequence, expiry,
  max_priority_fee_per_gas, max_fee_per_gas, gas_limit,
  account_changes, calls, metadata, payer
]))
```

The `sender` field in the payer signature hash MUST be the resolved sender address. In the EOA path (`sender` empty in the wire format), the recovered sender address (from `sender_auth` ecrecover, see [Validation](#validation)) MUST be substituted into the `sender` position before computing this hash; it MUST NOT be encoded as the empty wire-format value. This binds the payer's signature to the specific resolved sender and prevents cross-sender replay of payer signatures (see [Payer Security](#security-considerations)). The `payer` field MUST also be included so the payer's signature is bound to the account being charged; without it, a payer authorization could be redirected to any other account that authorizes the same actor with SPONSOR_PAYER scope (e.g., via the [delegate authenticator](#delegate-authenticator)).

#### Payer Modes

Gas payment and sponsorship are controlled by two independent fields.

**`payer`**, the sender's commitment regarding the gas payer, included in the sender's signed hash:

| Value | Mode | Description |
|-------|------|-------------|
| empty | Self-pay | Sender pays their own gas |
| `payer_address` (20 bytes) | Sponsored | Sender binds tx to a specific sponsor |

**`payer_auth`** uses the same `authenticator || data` format as `sender_auth`:

| `payer` | `payer_auth` | Payer Address | Validation |
|---------|-------------|---------------|------------|
| empty | empty | `sender` | Self-pay: no separate `payer_auth`; the resolved sender actor MUST have SELF_PAYER scope |
| `sender` address | `authenticator (20) \|\| data` | `sender` | Self-pay via a dedicated gas key: payer account == sender. Reads the `payer_auth`-resolved actor on the account, which MUST have SELF_PAYER scope |
| other address | `authenticator (20) \|\| data` | `payer` field | Sponsored (payer != sender): any authenticator. Reads payer's actor config, validates against `payer` address, and requires SPONSOR_PAYER scope |

### Transaction Metadata

The `metadata` field is optional opaque bytes for attaching attribution or annotation data to a transaction, for example builder/app attribution, a payment reference or memo, or a commitment to off-chain data. Legacy transactions carry such data as a "data suffix" appended to `tx.input`; because [calls](#call-phases) replace the single input blob, `metadata` provides the equivalent home.

`metadata` is part of the signed transaction (covered by both [signature payloads](#signature-payload)) and is charged per byte through `tx_payload_cost`. It does not affect validation or execution. Producers MAY use any encoding.

### Account Changes

The `account_changes` field is an array of typed entries for account creation and actor management:

| Type | Name | Description |
|------|------|-------------|
| `0x00` | Create | Deploy a new account with initial actors (must be first, at most one) |
| `0x01` | Config change | Actor management: authorizeActor, revokeActor |
| `0x02` | Delegation | Set code delegation via the delegation indicator (at most one per transaction) |

Create and delegation entries are authorized by the transaction's `sender_auth`; there is no separate authorization field. The initial `actorId`s for create entries are salt-committed to the derived address. Delegation requires the sender to be the account's implicit EOA actor and admin (`scope == 0x00`). Config change entries carry their own `auth` and use a sequence counter for deterministic cross-chain ordering. Nodes SHOULD enforce a configurable per-transaction limit on the number of config change entries (mempool rule).

#### Create Entry

New smart contract accounts can be created with pre-configured actors in a single transaction. The `code` is placed directly at the account address; it is not executed during deployment. The account's initialization logic runs via `calls` in the execution phase that follows:

```
rlp([
  0x00,               // type: create
  user_salt,          // bytes32: User-chosen uniqueness factor
  code,               // bytes: Runtime bytecode placed at account address
  initial_actors      // Array of [actorId, authenticator, scope, policyData] tuples
])
```

Each initial actor carries an `actorId`, `authenticator`, `scope` (`uint8`; `0x00` = unrestricted admin), and `policyData` (empty, or `manager ‖ commitment` when `POLICY` is set), all committed to the derived address (see [Address Derivation](#address-derivation)). Two things are **not** expressible here: `expiry`, and a self-referential `manager = account` (the account address is not yet known at commitment time). Both are added post-creation with a config change entry, which MAY accompany the create entry in the same `account_changes` array for atomic setup.

##### Address Derivation

Addresses are derived using the CREATE2 address formula with the Account Configuration Contract (`ACCOUNT_CONFIG_ADDRESS`) as the deployer. The `initial_actors` MUST be provided already sorted by `actorId` in strictly ascending order, which keeps derivation deterministic and rejects duplicate `actorId`s:

```
// initial_actors MUST already be sorted by actorId (strictly ascending); reject otherwise

actors_commitment = keccak256(
    actorId_0 || authenticator_0 || scope_0 || policyData_0 ||
    ...
    actorId_n || authenticator_n || scope_n || policyData_n
)

effective_salt = keccak256(user_salt || actors_commitment)
deployment_code = DEPLOYMENT_HEADER(len(code)) || code
address = keccak256(0xff || ACCOUNT_CONFIG_ADDRESS || effective_salt || keccak256(deployment_code))[12:]
```

The per-actor contribution is `actorId (32) || authenticator (20) || scope (1) || policyData` (empty when `POLICY` unset, or exactly 52 bytes — `manager (20) ‖ commitment (32)` — when set). The per-actor length is fully determined by `scope`, so the concatenation is unambiguous. Expiry does not participate.

`DEPLOYMENT_HEADER(n)` is a fixed 14-byte EVM loader that returns the trailing code (see [Appendix: Deployment Header](#appendix-deployment-header)). On non-8130 chains, `createAccount()` constructs `deployment_code` and passes it as init_code to CREATE2; on 8130 chains, the protocol constructs the same `deployment_code` for address derivation but places `code` directly. Callers only provide `code`.

##### Validation (Create Entry)

When a create entry is present in `account_changes`:

1. Parse `[0x00, user_salt, code, initial_actors]` where each entry is `[actorId, authenticator, scope, policyData]`. `scope` is stored verbatim. Apply `authorizeActor`'s frozen `policyData` rule: reject unless `policyData` is exactly `manager (20) ‖ commitment (32)` when `scope & POLICY != 0`, or empty otherwise. `expiry` is not accepted.
2. Require `initial_actors` sorted by `actorId` strictly ascending; reject otherwise (also rejects duplicates).
3. Reject if `code` is empty or `len(code) > MAX_CODE_SIZE` ([EIP-170](./eip-170.md): 24576 bytes).
4. Use `initial_actors` in the provided (sorted) order.
5. Compute `actors_commitment`, `effective_salt`, `deployment_code`, and `expected` per [Address Derivation](#address-derivation).
6. Require `sender == expected`.
7. Require CREATE2 freshness: `code_size(sender) == 0` and `nonce(sender) == 0`.
8. Validate `sender_auth` against one of `initial_actors` (resolved actorId and authenticator must match an entry).

#### Config Change Entry

Config change entries manage the account's actors. Each entry includes a `chain_id` field where `0` means valid on any chain, allowing replay across chains to synchronize actor state.

##### Config Change Format

```
rlp([
  0x01,               // type: config change
  chain_id,           // integer (EIP-155); 0 = valid on any chain. Hashed as uint256 in the signed digest
  sequence,           // uint64: monotonic ordering
  actor_changes,      // Array of actor changes
  auth                // Signature from an actor valid at this sequence
])

actor_change = rlp([
  change_type,          // uint8: operation type (see below)
  actorId,              // bytes32: actor identifier
  data                  // bytes: operation-specific, ABI-encoded
])
```

The operation-specific `data` is an opaque `bytes` blob encoded with the contract ABI, so it decodes identically whether applied natively or via `applySignedActorChanges()`, and is hashed as `keccak256(data)` in the [Config Change Signature Payload](#config-change-signature-payload).

**Operation types**:

| change_type | Name | `data` | Description |
|-------------|------|--------|-------------|
| `0x01` | `authorizeActor` | `abi.encode(ActorConfig config, bytes policyData)` (see [`ActorConfig`](#reference-implementation)) | Authorize a new actor. Writes the actor config with `authenticator`, `scope`, and `expiry` (`0` = no expiry) verbatim (unknown scope bits as-is), reserved bytes zeroed. If `POLICY` is set, requires `policyData = manager ‖ commitment` (exactly 52 bytes) and writes those slots; otherwise requires empty `policyData` and clears policy slots. Does **not** enforce scope-combination exclusivity. Emits `ActorAuthorized` whose `actorData` is 32 bytes (`authenticator ‖ scope ‖ expiry ‖ reserved`) when `POLICY` is unset, or 84 bytes (appending `manager ‖ commitment`) when set. |
| `0x02` | `revokeActor` | empty (`0x`) | Revoke an existing actor. Clears the actor config (and `policy_commitment`/`policy_manager`). For the implicit EOA actor (`actorId == bytes32(bytes20(account))`), instead sets `DEFAULT_EOA_REVOKED`. Emits `ActorRevoked`. |

#### Config Change Authorization

The `auth` must be valid against the account's actor configuration *after all previous entries in the list have been applied*, and the authorizing actor must be **admin** (`scope == 0x00`). The sequence number is scoped by `chain_id`: `0` uses the multichain channel (valid on any chain), a specific `chain_id` uses that chain's local channel. The channels double as the initialized flag: creation and import set the local channel to `1`, and any applied change bumps whichever channel it used.

##### Config Change Signature Payload

```
TYPEHASH = keccak256("SignedActorChanges(address account,uint256 chainId,uint64 sequence,ActorChange[] actorChanges)ActorChange(uint8 changeType,bytes32 actorId,bytes data)")
ACTORCHANGE_TYPEHASH = keccak256("ActorChange(uint8 changeType,bytes32 actorId,bytes data)")

actorChangeHashes = [keccak256(abi.encode(ACTORCHANGE_TYPEHASH, changeType, actorId, keccak256(data))) for each actorChange]
actorChangesHash = keccak256(abi.encodePacked(actorChangeHashes))

digest = keccak256(abi.encode(TYPEHASH, account, chainId, sequence, actorChangesHash))
```

Domain separation from transaction signatures (`AA_TX_TYPE`, `AA_PAYER_TYPE`) is structural: transaction hashes use `keccak256(type_byte || rlp([...]))`, which cannot produce the same prefix as `abi.encode(TYPEHASH, ...)`. The `auth` follows the same [Signature Format](#signature-format) as `sender_auth`, validated against the account's actor state at that point in the sequence.

##### Account Config Change Paths

The same signed actor change can be applied through two paths:

- **`account_changes` (tx field)**: processed by the protocol before code deployment on 8130 chains.
- **`applySignedActorChanges()` (EVM)**: applied during EVM execution on any chain, including non-8130 chains and ERC-4337 deployments.

Both carry the same signed actor changes, share the same `change_sequence` counters, and are equally portable (`chain_id 0` for cross-chain or a specific `chain_id` for chain-local). Anyone can call these functions; authorization comes from the signed operation, not the caller. `authorizeActor`/`revokeActor` and delegation are blocked when the account is locked; lock/unlock use `applySignedLockChanges` (see [Account Lock](#account-lock)).

#### Delegation Entry

Delegation entries set [EIP-7702](./eip-7702.md)-style code delegation for the sender's account, replacing the need for an `authorization_list`. Delegation is authorized by the transaction's `sender_auth`; no separate signature is required. The sender must have been **authenticated via the native secp256k1 path** (the EOA path or `K1_AUTHENTICATOR`; mirroring [Implicit EOA Rule Scoping](#security-considerations)), with `actorId == bytes32(bytes20(sender))` and admin (`scope == 0x00`). A non-secp256k1 self authenticator does not qualify, keeping delegation authority ECDSA/7702-portable.

##### Delegation Format

```
rlp([
  0x02,               // type: delegation
  target              // address: delegate to this contract, or address(0) to clear
])
```

Delegation is only permitted when `code_size(sender) == 0` (empty account) or `code(sender)` starts with the delegation designator `0xef0100` (updating an existing delegation). It will not replace non-delegation bytecode. When `target` is `address(0)`, the delegation indicator is cleared and the account's code hash is reset to the empty code hash. Successful delegation updates emit a protocol-injected `DelegationApplied(account, target)` receipt log.

#### Execution (Account Changes)

`account_changes` entries are processed in order before call execution:

1. **Create entry** (if present): Register `initial_actors` in Account Config storage for `sender`, writing each actor's config with the given `authenticator` and `scope` verbatim and `expiry = 0`. When `scope & POLICY != 0`, also write `policy_manager`/`policy_commitment` from `policyData`. A tuple naming the self-actorId with `K1_AUTHENTICATOR` writes its `scope` into the inline default-EOA fields instead (`expiry = 0`). Mark the account initialized (local change-sequence channel `= 1`). Initialize lock state to safe defaults (`LOCKED`/`UNLOCK_INITIATED` clear, `lock_union = 0`). Set `DEFAULT_EOA_REVOKED` unless a native secp256k1 owner is among `initial_actors`. Place `code` at `sender`.
2. **Config change entries** (if any): Apply operations in entry order. Reject if account is locked.
3. **Delegation entries** (if any): Require admin EOA-actor delegation authority (see [Delegation Entry](#delegation-entry)). Reject if account is locked. For each entry, set `code(sender) = 0xef0100 || target` (or clear if `target` is `address(0)`). Reject if account has non-delegation bytecode.

### Execution

#### Call Execution

The protocol dispatches calls directly from `sender` to each call's `to` address:

| Parameter | Value |
|-----------|-------|
| `from` (caller) | `sender` |
| `to` | `call.to` |
| `tx.origin` | `sender` |
| `msg.sender` at target | `sender` |
| `msg.value` | 0 |
| `data` | `call.data` |

Calls carry no ETH value. ETH transfers are initiated by the account's wallet bytecode via the CALL opcode, so removing protocol-level value from calls loses no capability.

##### Call Phases

`calls` is a two-level structure: an ordered array of **phases**, where each phase is an ordered array of individual calls (`[[call, ...], [call, ...]]`). This gives two levels of atomicity: calls within a phase are all-or-nothing, while phases commit independently in sequence.

Phases execute in order from a single gas pool (`gas_limit`). Within each phase, calls execute in order and are **atomic**: if any call in a phase reverts, all state changes for that phase are discarded and remaining phases are **skipped**. Completed phases **persist**.

**Phase 0 and account changes.** `account_changes` are applied immediately before call phase 0 (`calls[0]`) and are atomic with it: if phase 0 reverts, all account changes are reverted along with it, remaining phases are skipped, and the storage-application cost is not charged (see [Intrinsic Gas](#intrinsic-gas)). To decouple account changes from the calls, include an empty phase 0 (`[[], ...]`), which cannot revert; empty `calls` behaves identically. Wallets SHOULD emit an empty phase 0 whenever `account_changes` are present and no payment leg is intended, so that a reverting call cannot roll back an actor rotation (e.g. a compromised key griefing its own revocation); binding account changes to a non-empty phase 0 is a deliberate sponsor-protection idiom, not the default.

**Policy gate.** When the transaction's authenticating actor has `POLICY` set, each call is gated before dispatch. The protocol resolves the actor's allowed target (`policy_manager(sender, actorId)`) once at the start of `calls` execution, and that snapshot gates every call in every phase, including phase 0. If `call.to` is not that address, the call is **not dispatched** and fails deterministically with the protocol revert `ActorPolicyViolation(bytes32 actorId, address target)`:

```solidity
error ActorPolicyViolation(bytes32 actorId, address target);
```

The frame's return data is `abi.encodeWithSelector(ActorPolicyViolation.selector, actorId, call.to)`. This is a consensus-level result, not a validity error, so standard atomicity applies: the enclosing phase's state changes roll back, later phases are skipped, and the phase is reported as failed in `phaseStatuses`. Only work already performed is charged; the undispatched call body costs nothing and the transaction is still included with its nonce consumed.

**Common patterns**: `[[call]]` (simple call); `[[call_a, call_b]]` (atomic batch); `[[sponsor_payment], [user_action]]` (sponsor in phase 0 committed, user action in phase 1 skipped if sponsor fails).

#### Transaction Context

The Transaction Context precompile at `TX_CONTEXT_ADDRESS` provides read-only access to the current transaction's metadata during call execution; it is populated only while `calls` are dispatched. Gas is a base cost plus 3 gas per 32 bytes returned, matching `CALLDATACOPY`.

| Function | Returns | Available |
|----------|---------|-----------|
| `getTransactionSender()` | `address`, the account executing calls (`sender`) | Execution only |
| `getTransactionPayer()` | `address`, gas payer | Execution only |
| `getTransactionSenderActorId()` | `bytes32`, authenticated actor's actorId | Execution only |

A policy target combines `getTransactionSender()` and `getTransactionSenderActorId()`, then reads the actor's gate target and signed `commitment` via `getPolicy(account, actorId)` and validates presented parameters against the commitment. On non-8130 chains there is no code at `TX_CONTEXT_ADDRESS`; STATICCALL returns zero/default values.

### Portability

The system splits into storage and authentication layers with different portability:

| Component | 8130 chains | Non-8130 chains |
|-----------|-------------|-----------------|
| **Account Configuration Contract** | Protocol reads storage directly for validation; EVM interface available | Standard contract (ERC-4337 compatible factory) |
| **Authenticator Contracts** | Protocol calls authenticators via STATICCALL | Same onchain contracts callable by account config contract and wallets |
| **Code Delegation** | Delegation entry in `account_changes` (EOA-only authorization in this version) | Standard [EIP-7702](./eip-7702.md) transactions (ECDSA authority) |
| **Transaction Context** | Precompile at `TX_CONTEXT_ADDRESS` | No code at address; STATICCALL returns zero/default values |
| **Nonce Manager** | Precompile at `NONCE_MANAGER_ADDRESS` | Not applicable; nonce management by existing systems (e.g., ERC-4337 EntryPoint) |

All contracts are deployed at deterministic CREATE2 addresses across chains (see [Contract Pinning](#contract-pinning)).

### Validation

All authorization — actor resolution, scope, expiry, nonce scope, and the policy-gate target — is evaluated against the transaction's **effective actor state**: persisted Account Configuration storage statically composed with the transaction's own `account_changes`, applied in order. Composition validates each config-change entry's auth and sequence but executes no EVM code; authorization derives from the signature chain, not from persistence. The composed changes are applied to storage immediately before call phase 0 — unless phase 0 reverts, which rolls them back.

Authenticating a single `auth` blob (`sender_auth`, `payer_auth`, or a config-change `auth`) against effective actor state:

1. **Resolve identity.** If `sender` empty, ecrecover derives the sender address (EOA path) with `actorId = bytes32(bytes20(sender))`. If `sender` set, read the first 20 bytes of the blob as the authenticator address.
2. **Authenticate.** For the EOA path, ecrecover was performed in step 1. For `K1_AUTHENTICATOR`, the protocol natively ecrecovers from `data`, returning `actorId = bytes32(bytes20(recovered_address))`. For all other authenticators, call `authenticator.authenticate(hash, data)` via STATICCALL, returning `actorId` (or `bytes32(0)` for invalid). `address(0)` is never a valid authenticator selector.
3. **Resolve the actor.** *Self-actor (native secp256k1) rule*: if step 2 used the native secp256k1 path and `actorId == bytes32(bytes20(account))`, resolve the self-actor from its default-EOA config: reject if `DEFAULT_EOA_REVOKED` is set; otherwise take `scope`/`expiry` from that config. Otherwise read the actor config, reject if its reserved bytes are nonzero (version gate), and require that the stored authenticator address matches the effective authenticator. In either case, if the resolved `expiry` is non-zero, require `block.timestamp <= expiry`; an expired actor is rejected.
4. **Check scope** against the context being authorized, per [Actor Scope](#actor-scope).
5. **Check nonce scope** (sender-context only, when `nonce_key != NONCE_KEY_MAX`): require the resolved actor be admin or carry `NONCE`, per [Actor Nonce Scope](#actor-nonce-scope).

#### Mempool Acceptance

1. Parse and structurally validate `sender_auth`. Verify `account_changes` contains at most one create entry (type `0x00`, must be first) and at most one delegation entry (type `0x02`). Nodes SHOULD enforce a configurable limit on config change entries (type `0x01`).
2. Resolve sender: if `sender` set, use it; if empty, ecrecover from `sender_auth`.
3. Determine effective actor state: if a create entry is present, verify address derivation and `code_size(sender) == 0` and use `initial_actors`; otherwise read from Account Config storage and compose any config-change/delegation entries (reject if the account is locked; skip already-applied config entries; for delegation verify `code_size(sender) == 0` or an existing delegation designator).
4. Validate `sender_auth` against the resulting actor state (steps 1–5 above), checking sender-context scope and nonce scope. If delegation entries are present, the resolved actor must additionally hold admin EOA-actor delegation authority (see [Delegation Entry](#delegation-entry)).
5. Resolve payer from `payer` and `payer_auth`, checking payer scope:
   - `payer` empty, `payer_auth` empty: self-pay; payer is `sender`; require SELF_PAYER on the resolved sender actor.
   - `payer` = `sender` with `payer_auth`: self-pay via a dedicated gas key; validate `payer_auth` against the account and require SELF_PAYER.
   - `payer` = a different address: sponsored; validate `payer_auth` against the `payer` address and require SPONSOR_PAYER.
6. Verify nonce, payer ETH balance, and expiry. Both `expiry` fields MUST be satisfied: the transaction `expiry` (inclusion validity) and the resolved actor's `expiry` (key liveness). For standard keys (`nonce_key != NONCE_KEY_MAX`), require `nonce_sequence == current_sequence(sender, nonce_key)`. For a nonce-free key (`NONCE_KEY_MAX`), skip the nonce check, require `nonce_sequence == 0` and non-zero `expiry`, reject if `expiry` is farther out than `NONCE_FREE_EXPIRY_WINDOW`, and deduplicate by the [Replay Identifier](#replay-identifier).
7. Mempool threshold: gas payer's pending count below node-configured limits.
8. Apply [Mempool Replacement](#mempool-replacement) rules.

Nodes admit authenticators per the [Authenticator Acceptance](#authenticator-acceptance) model in force on the chain. Nodes MAY apply higher pending-transaction rate limits based on account lock state (see [Account Lock](#account-lock)): a locked `sender` with a stateless authenticator has a stable signature, and a locked `payer` running trusted bytecode that restricts ETH movement while locked bounds balance changes to gas fees.

#### Block Execution

1. If `account_changes` contains config change or delegation entries, read lock state for `sender` and reject if locked. If delegation entries are present, require admin EOA-actor delegation authority.
2. ETH gas deduction from payer (`sender` for self-pay). Invalid if payer has insufficient balance.
3. If `nonce_key != NONCE_KEY_MAX`, increment the nonce for `(sender, nonce_key)`; otherwise apply nonce-free replay processing.
4. Set transaction context on the Transaction Context precompile (sender, payer, actorId).
5. If `code_size(sender) == 0` and no create entry and no delegation entry is present, auto-delegate `sender` to `DEFAULT_ACCOUNT_ADDRESS`. Auto-delegation persists even if call phase 0 subsequently reverts.
6. Apply `account_changes` entries in order (see [Execution (Account Changes)](#execution-account-changes)) and then execute call phase 0 (`calls[0]`) within a single atomic scope. If phase 0 reverts: roll back both the account changes and phase 0's state, apply the phase-0 revert charging rule (see [Intrinsic Gas](#intrinsic-gas)), skip step 7, and set receipt `status` / `phaseStatuses[0]` to `0x00`. The config-change sequence counters advance only on commit, so a reverted phase 0 consumes no change sequence; the nonce consumed in step 3 is not restored. An empty phase 0 (`[[], ...]`) cannot revert, so the account changes always commit.
7. Execute `calls[1..]` per [Call Execution](#call-execution) semantics.

Unused gas from `gas_limit` is refunded to the payer. For step 6, the protocol SHOULD inject log entries into the receipt (`ActorAuthorized`, `ActorRevoked`, `AccountCreated`, `DelegationApplied`) matching the events in the [Reference Implementation](#reference-implementation), following the protocol-injected log pattern of [EIP-7708](./eip-7708.md). These logs are emitted only for 8130 transactions.

### RPC Extensions

- **`eth_getTransactionCount`** — extended with an optional `nonceKey` parameter (`uint256`) to query 2D nonce channels, read from the Nonce Manager precompile.
- **`eth_getTransactionReceipt`** — AA receipts add `payer` (address), `status` (uint8; `0x01` = phase 0 succeeded and durable state persisted, `0x00` = phase 0 reverted and account changes rolled back; auto-delegation, nonce consumption, and gas payment persist regardless; `gasUsed` includes `payer_auth_cost`), and `phaseStatuses` (uint8[]; per-phase `0x01`/`0x00`, phases after a revert reported `0x00`, `phaseStatuses[0] == status`).
- **`eth_estimateGas`** / **`eth_call`** — accept the AA transaction fields alongside the standard request object and price the request as an `AA_TX_TYPE` transaction from an **unsigned** representative auth blob (authentication gas depends on the blob's shape, not a valid signature). The sender is taken from `sender` or the standard `from`; if both are present they MUST be equal.

### Contract Pinning

Following the pattern of [EIP-4788](./eip-4788.md), the system contracts are defined by their deployed bytecode rather than by prose. Each contract's **deployed runtime code is the canonical, normative artifact**: storage layout, slot derivation, and internal packing are defined by that bytecode and are not restated in this specification, and on any discrepancy the pinned bytecode is authoritative. Each contract is deployed at a deterministic CREATE2 address (fixed deployer and salt) so it resolves to the same address on every chain; a chain is compliant only if the code at each address matches the pinned bytecode.

The reference implementation lives at [8130-working-group/contracts](https://github.com/8130-working-group/contracts). The concrete pins — source commit, deployed runtime codehash, CREATE2 init-code hash, and resolved addresses — are **pending final audits** and will be fixed in this section before the EIP moves to Final.

| Default Account | `DEFAULT_ACCOUNT_ADDRESS` | `DefaultAccount.sol` |

| P-256 Authenticator | `P256_AUTHENTICATOR` | `P256Authenticator.sol` |
| Passkey Authenticator | `PASSKEY_AUTHENTICATOR` | `WebAuthnAuthenticator.sol` |
| Delegate Authenticator | `DELEGATE_AUTHENTICATOR` | `DelegateAuthenticator.sol` |

secp256k1 (`K1_AUTHENTICATOR`, `address(1)`) is built into the Account Configuration contract via native `ecrecover` and has no standalone contract. The canonical authenticator set is enumerated per fork; adding an algorithm adds a row here for the fork that introduces it.

### Appendix: Deployment Header

`DEPLOYMENT_HEADER(n)` is a 14-byte EVM loader that copies trailing code into memory and returns it, encoding code length `n` into its `PUSH2` instructions:

```
DEPLOYMENT_HEADER(n) = [
  0x61, (n >> 8) & 0xFF, n & 0xFF,     // PUSH2 n        (code length)
  0x60, 0x0E,                          // PUSH1 14       (offset: code starts after 14-byte header)
  0x60, 0x00,                          // PUSH1 0        (memory destination)
  0x39,                                // CODECOPY
  0x61, (n >> 8) & 0xFF, n & 0xFF,     // PUSH2 n        (code length)
  0x60, 0x00,                          // PUSH1 0        (memory offset)
  0xF3                                 // RETURN
]
```

The create entry only supports runtime bytecode; delegation is set via delegation entries (type `0x02`) in `account_changes`.

## Rationale

### Why Authenticator Contracts?

The authenticator returns the `actorId` rather than accepting it as input, so the protocol needs no algorithm-specific logic and all authenticators share one `authenticate(hash, data)` interface. A fixed canonical set (rather than per-node discretion) gives wallets a shared baseline accepted by any compliant node. Public keys are not stored onchain — authenticators recover the `actorId` from calldata — keeping per-actor state to a single config read regardless of key size, which matters most for large post-quantum credentials.

### Why Admin Is Scope Zero

Admin is `scope == 0x00` rather than a dedicated grant bit because any key that can rewrite an actor's config can grant itself `scope == 0x00`; config authority is therefore already equivalent to unrestricted authority, and naming admin as the absence of restriction makes that self-escalation explicit. It also gives every account a natural root, with restricted keys strictly grants below it.

### Design Layering

The immutable contract enforces only timeless structure at deployment (admin signer, reserved-bytes-zero, well-formed `policyData`) and stores scope verbatim. Grants can grow because reads fail closed on unknown bits, so new grants (e.g. `NONCE`) use spare bits without changing the frozen surface, and combination semantics are checked at the point of use so an unsatisfiable combo is inert. Signing semantics evolve at the account layer.

### Consolidated Design Notes

One line each; the Specification carries the detail:

- **Gas schedule.** The formula structure is normative; the numbers are a recommended schedule a chain MAY reprice or replace with Metered Calls (identical validity and state roots).
- **payer_auth outside gas_limit.** `payer_auth` is payer-chosen and excluded from both signature hashes, so isolating it keeps gas available to `calls` a function of sender-signed fields alone; the payer reimburses it regardless.
- **SELF_PAYER vs SPONSOR_PAYER.** The split separates what the spend can *buy*: self-pay funds only the account's own transactions, sponsorship funds arbitrary third parties (a transferable paymaster authority), so cross-account payment is default-deny.
- **2D nonce + `NONCE_KEY_MAX`.** Parallel lanes avoid contention; nonce-free is coordination-free for session keys, and `NONCE` reserves ordered channels for actors that want them.
- **Account lock.** A frozen actor set lets nodes cache actor state and raise mempool rate limits; a locked payer with trusted bytecode bounds balance changes to gas fees.
- **CREATE2 creation.** Deterministic cross-chain addresses, counterfactual funding, and `initial_actors` in the salt prevent front-running of actor assignment.
- **Delegation via account changes.** [EIP-7702](./eip-7702.md)-style delegation under `sender_auth`, restricted to the native secp256k1 path so it stays portable via standard [EIP-7702](./eip-7702.md) transactions.
- **Call phases.** Two atomic batching levels without per-call flags: all-or-nothing within a phase, payment persists across phases.
- **No value in calls.** Every account has wallet bytecode, so ETH transfers route through wallet code via `CALL`; the protocol never moves ETH for the sender.
- **Metadata field.** A first-class, signed home for the traditional `tx.input` data-suffix now that `calls` has no trailing location.
- **Transaction Context precompile.** Immutable context via a zero-write, pull-model, forward-compatible precompile.
- **Charge validation unconditionally.** Config-change signatures authorize the transaction whether or not changes persist, so charging only on application would let a transaction consume authenticator work and revert out of paying.
- **Account changes atomic with phase 0.** Rolling account changes back with a phase-0 revert bounds a sponsor's worst-case loss and closes the paid-for-create leak; an empty phase 0 opts out. Abort refund is profile-specific: Explicit Accounting pre-prices state growth, so a rollback refunds the application share (no growth occurred); Metered Calls needs no rule because EVM metering already charges reverted scopes for work performed.

### External Account Factories

Account creation, import, signed actor changes, and locking are ordinary EVM entry points on the Account Configuration Contract, so external factories can compose them to mint accounts into a desired end state. This is always possible in EVM but is **not** available on the 8130 transaction path.

*Non-normative future work:* once [EIP-7819](./eip-7819.md) is adopted, the create entry could emit an [EIP-7702](./eip-7702.md) delegation prefix and deploy from a single canonical external factory, extending the delegation account change to all authenticator types rather than the native secp256k1 EOA only.

## Backwards Compatibility

No breaking changes. Existing EOAs and smart contracts function unchanged. Adoption is opt-in:

- EOAs continue sending standard transactions.
- ERC-4337 infrastructure continues operating.
- Accounts gain AA capabilities by configuring actors. EOAs sending their first AA transaction are auto-delegated to `DEFAULT_ACCOUNT_ADDRESS` if they have no code, and MAY override with a delegation entry in `account_changes` (EOA-only authorization), a standard [EIP-7702](./eip-7702.md) transaction, or a create entry for custom wallet implementations.

The actor-config layout, the address-derivation commitment, and the ABI surface (typehashes, events, `importAccount`/`applySignedActorChanges` signatures) are defined by this specification and the pinned contract. Because 8130 has no prior deployment, there is no live actor state written under an earlier format to migrate.

## Reference Implementation

The Account Configuration Contract's deployed bytecode is the canonical ABI surface and normative artifact (see [Contract Pinning](#contract-pinning)); the full source (pending final audits) lives at [8130-working-group/contracts](https://github.com/8130-working-group/contracts) (`AccountConfiguration.sol`). The authenticator interface is the minimal contract every authenticator implements:

```solidity
interface IAuthenticator {
    function authenticate(
        bytes32 hash,
        bytes calldata data
    ) external view returns (bytes32 actorId);
}
```

The `IAccountConfiguration` structs (`ActorConfig`, `InitialActor`, `Actor`, `ActorChange`), events (`ActorAuthorized`, `ActorRevoked`, `AccountCreated`, `AccountImported`, `DelegationApplied`, `AccountLocked`, `AccountUnlockInitiated`), and functions (`createAccount`, `computeAddress`, `importAccount`, `applySignedActorChanges`, `applySignedLockChanges`, `verifySignature`, `authenticateActor`, `getActorConfig`, `getPolicy`, `getChangeSequences`, `getLockStatus`, and related views) are defined by the pinned contract in that repository. The precompile interfaces are:

```solidity
interface ITransactionContext {  // TX_CONTEXT_ADDRESS; read-only
    function getTransactionSender() external view returns (address);
    function getTransactionPayer() external view returns (address);
    function getTransactionSenderActorId() external view returns (bytes32);
}

interface INonceManager {        // NONCE_MANAGER_ADDRESS; read-only
    function getNonce(address account, uint256 nonceKey) external view returns (uint64);
}
```

`ITransactionContext` gas is a base cost plus 3 gas per 32 bytes returned. `INonceManager` reads are priced as a cold SLOAD (first read of a given `(account, nonceKey)` in the transaction) or a warm SLOAD thereafter, per [EIP-2929](./eip-2929.md).

## Security Considerations

**Validation Surface**: For canonical authenticators, invalidators are actor-config changes and nonce consumption.

**Replay Protection**: For standard and 2D transactions, inclusion increments `(sender, nonce_key)`, so a given `(sender, nonce_key, nonce_sequence)` is included at most once. Nonce-free mode has no nonce slot, so replay protection relies on short-lived `expiry` and deduplication by the fee- and signature-invariant [Replay Identifier](#replay-identifier); builders MUST NOT include two transactions with the same `(sender, replay_id)`. The full transaction hash MUST NOT be used: it commits to fee fields and the non-deterministic auth blobs that `replay_id` excludes, so a fee bump, re-signed `payer_auth`, or malleable `sender_auth` all resolve to the same `replay_id`. `expiry` is part of `replay_id`, so it cannot be extended via a fee-bump replacement.

**Actor Scope and Policy**: Scope grants are protocol-enforced after authenticator execution (fail closed); the policy gate is enforced during execution (`ActorPolicyViolation`). A policy-bearing actor's resolved target is fully trusted — a buggy or malicious manager can do anything its own authority allows — so accounts SHOULD point restricted keys only at audited, non-upgradeable managers; matching `keccak256(params)` to the commitment is the target's responsibility. `revokeActor` clears the actor config and both policy slots, immediately stopping the key; target-held parameters are uninstalled through the target, with `expiry` bounding the interim window.

**Actor Management**: Config changes require an admin (`scope == 0x00`) signer; the implicit EOA actor is admin, revocable via portable config change, and all modification paths are blocked when locked. Prefer non-expiring admins and apply `expiry` only to restricted keys; a sole expiring admin bricks the account.

**Implicit EOA Rule Scoping**: The implicit EOA rule only applies when authentication used the native secp256k1 path and `DEFAULT_EOA_REVOKED` is unset. Generic authenticators MUST NOT satisfy the implicit branch even if they return `bytes32(bytes20(sender))`, otherwise an arbitrary authenticator could authenticate as any EOA whose implicit slot was never written.

**actorId Binding**: The protocol checks that the returned `actorId` maps back to that authenticator in the actor config, preventing a malicious authenticator from claiming another's actors.

**Payer Security**: `AA_TX_TYPE` vs `AA_PAYER_TYPE` domain separation and the signed `payer` field prevent signature reuse between roles; SELF_PAYER vs SPONSOR_PAYER prevents a self-paying key from being repurposed as an unbounded sponsor. Payer exposure is bounded by signed fee fields, and payer authentication is metered separately. The payer hash binds to the *resolved* sender: in the EOA path the recovered sender MUST be substituted into the `sender` position before hashing, otherwise two EOAs with identical data would produce identical payer hashes and one could reuse the other's payer signature to drain its gas deposit (the 2D nonce does not prevent this, since each attacker controls their own `nonce_key`/`nonce_sequence`).

**Account Creation Security**: `initial_actors` are salt-committed, preventing front-running. Wallet bytecode should be inert when uninitialized. The create entry applies only to CREATE2-fresh addresses (without the nonce check it could be replayed against an EOA with history at the counterfactual address). Direct code placement bypasses the [EIP-170](./eip-170.md) `MAX_CODE_SIZE` check, so the protocol enforces `len(code) <= MAX_CODE_SIZE` explicitly.

**Surviving signed changes**: A config-change entry from a reverted phase 0 did not consume its sequence and remains a valid signed artifact anyone may apply via `applySignedActorChanges`. Wallets MUST NOT assume a reverted transaction's payload is dead; the skip rule handles a retry that finds it already applied. Under Explicit Accounting, a rolled-back application's slot reads go uncharged within the refunded share; this is bounded by payload cost scaling with entry count and the config-change entry cap, and is accepted as a schedule simplification.

**Visibility / gated keys**: `account_changes` apply before phase 0, so a revoked actor is already inactive during phase 0 and later phases; a phase-0 revert rolls them back, so exposure is one transaction wide and mirrors `sender_auth`. The policy gate covers phase 0 with no exemptions, and `POLICY | SPONSOR_PAYER` leaves sponsor authority ungated (such a key may co-sign as payer for third parties while unable to originate token payments for its own account).
